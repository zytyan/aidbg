
## 核心目标
提供client-server模型的MCP工具，client作为stdio的MCP入口，client与server使用protobuf的gRPC通信。对于核心调试工具服务端，仅支持x64和ARM64架构的Linux，对于与Agent通信的客户端，需要额外支持Windows。

初步设计中，由于主要在内网使用，所以服务端和客户端通信使用明文，不采取TLS加密。
### 关键设计
整体项目为rust项目，设计上提供两套接口，一套MCP工具接口用于AI使用简单的工具，并通过schema增强协同解码能力（若可能）；另一套为ts接口，ts采取强类型强校验，保证简单的同时把检查提前到脚本编译期。

由于是异步工具，但目前支持工具主动发送消息的Agent太少，所以对于所有在阻塞的异步操作，**必须**每次返回正在阻塞的操作，催促AI完成。一旦client主动退出，或异常退出，30秒内没有重连，则服务端要放弃对目标进程的attach。

工具要同时支持live调试（run或attach）和coredump调试。为了统一接口，live和coredump的类型定义应一致，但对于不支持的操作，应该直接抛异常（如core调试中，`dbg.coredump`的应该抛出`NotSupport`异常。

由于已经使用了MCP作为核心接口，将不会再支持CLI接口，CLI接口应从项目中删除，仅维护MCP接口即可。

虽然我预期支持跑在目标进程&调试器内的Unicorn，但是这个功能过于复杂了，暂时不支持它。但如果将来支持`dbg.unicornBreakpoint`系列应该需要支持core调试。

由于文档本身是跟着设计走的，并且AI没有长期记忆，所以对项目进行破坏性修改并不会引入什么问题。本次`proto`必须要进行大规模的破坏性重构，需要重新开发客户端与服务端，此次重构后，由于MCP接口量急剧减少，所以应该不会再有对proto的破坏性修改了。

一定要做好测试！测试环境主要在本机架构，除非特地要求，否则不需要到其它设备上或使用模拟器测试。

## 工具定义

- `run(path, arg)` 对标 gdb run
- `attach(pid)` 对标 gdb attach
- `script_run(src)`运行ts脚本，类型标注必须完善，否则编译检查不过（验证左移）
- `core_open`打开一个core，对标`gdb -c`
- `send_input(handler, data)` 向特定的handler发送消息，也就是向等在`console.waitInput`的线程发消息。
- `interrupt_input(handler, msg)`向特定的handler发送中断，js里表现为抛出异常，可以携带信息，此时异常信息会原样传回。
- `snapshot([tid])`
- `perf` 原样保留
- `ps` 作为查看进程的方式，类似`ps -ef`，但是不太重要，因为我已经有一个remote ssh MCP了。


MCP工具用于辅助，核心能力基本全在ts里。

MCP每次都要返回正在被AI暂停的线程和正等待AI输入的`handler`，确保AI不要忽略这件事。应有关键的提示告诉AI。

## ts层API定义

工具的核心是结构化调试，所以核心能力在于TypeScript，TypeScript由Rust构建的tsrs作为类型检查。为了规避AI幻觉，tsrs的类型验证是强制的（即类型左移）。同时，除了类型验证，也会对一些可检查的常量进行验证（如dwarf信息），尽可能做到减少幻觉造成的影响。使用tsrs剥离出原生js后，使用QuickJS执行。使用`rquickjs`crate作为QuickJS绑定库。

为保证文档清晰可读，减少维护成本，大部分ts类型定义均已从文档中移除，请从同目录下的`debugger.d.ts`获取实际定义。

### 全局导出

```ts
export const dbg: Debugger;
export const m: TypeSystem;
export const $: GlobalScope; // 保存一份额外的 .d.ts
export const console: Console;

```

### 核心类型：dbg
这是一个全局单例，是整个调试器里最核心的类型，对于每个调试实例（live调试或者core调试）都应该有且仅有一个。

```ts

interface Debugger {}
```


### 核心类型：`snapshot`

快照用于读取寄存器，获取调用栈和本地变量（若有dwarf信息）。这也是AI在首次遇到未知bug时的核心操作，先看看每个线程的寄存器和调用栈。
```ts
interface ThreadSnapshot {}

interface DebugSnapshot {}
```

全局命名空间 `$`，使用 `export`导出的名称，都会挂接到`$`下

```ts
export function myOnHit() {
	// ...
}

// 另一次script_run

$.myOnHit() // OK，可引用

$ = 1; // 静态报错，不允许覆盖全局命名空间
() => {
	let $ = 1; // 同静态报错，不允许遮蔽全局命名空间
    m = 1;
    dbg = 1; // 与上面相同，禁止覆盖、遮蔽全局命名空间，必须静态报错。
}

```

### 核心类型：globalScope&Console

这个是作为通用的全局作用域内容存在的，globalScope为`$`，而Console类型则作为交互与格式化使用


```ts
class GlobalScope {
	// 默认没有任何东西，但AI的script_run中每个导出变量都会出现在这里
	// 重复名称会覆盖原有元素，非常合理
	...
}
class Console {}

export const console: Console;
export const $: GlobalScope;
```
### 核心类型：Thread

线程是另一个核心类型，它代表被调试进程的一个系统级线程。它的生命周期应与系统线程绑定，当系统线程销毁后，对其status外的任何访问都应该直接抛出异常。与gdb不同，所有inferior call与syscall inject都必须绑定在某线程上。

```ts
interface Thread {}
```


### 扩展核心类型： `ControlledThread`

`ControllThread`属于继承了 Thread的扩展类型，表示该线程正在被调试器控制，可以进行单步执行等操作。

```ts
interface ControlledThread extends Thread {}
```


### 核心类型：`Memory`

Memory将会是处理内存的核心类型，它属于`dbg`下的一个只读成员`memory`。同样的，它也是单例，与目标进程的生命周期绑定。

```ts
export interface MemoryView {}
```

### 核心类型：`TypeSystem`

使用概念类似zod的声明式API，要求必须ES6及以上版本以提供声明顺序保证。考虑到使用QuickJS已经可以支持ES2020以上的版本，这里只是说明对顺序保证的需求。

该类型为整个设计中最复杂，最容易出错的地方，一定要做好测试。
- 单元测试：使用tsd做类型检查，确保预期声明与实际一致
- 集成测试：使用内部的gcc、clang进行编译，并使用实际的目标程序测试trace后的情况。正常路径需要不出错，不触发缺页。访问指针、数组、union等都应该正常。

#### 核心接口：`TypeSystem`

`TypeSystem`是整个类型系统里最核心的内容了，它负责将ts声明转换为实际可用的内存访问序列，实现JS <-> C 的双向转换。整个类型体操已经放入了`debugger.d.ts`中，接口为V1版本冻结，将来需要添加新功能时再增加设计。

整个类型系统是用于防止AI产生幻觉的，尽可能验证左移，将可能的幻觉在编译时就驱逐出去。

但是如果彻底结构化的话，类型设计就会过于复杂，所以不会特地防绕过类型系统，只防止幻觉导致的使用不匹配。

```ts
// TypeSystem：声明式类型构造接口。
interface TypeSystem {}

```

看来尚余匿名union没有处理，这确实是js力不能及之处，暂无有效方案。但问题不是特别大，只是无法使用dwarf。
```ts
const TLVArray = m.struct({
    type: m.u32(),
    length: m.u32(),
    value: m.array(m.u8(), ctx => ctx.length)
})

const TLVPtr = m.struct({
    type: m.u32(),
    length: m.u32(),
    value: m.array(m.u8(), ctx => ctx.length)
})

const BTree = m.struct({
    left: m.pointer(m.self()),
    right: m.pointer(m.self()),
    value: m.i32(),
})

const IP = m.struct({
    type: m.u8(),
    ip: m.union({
        v4: m.u32(),
        v6: m.array(m.u8(), 16),
    })
})
const Outer = m.struct({
    length: m.u32(),
    inner: m.struct({
        data: m.pointer(m.u8(), ctx => ctx.$parent.length)
    })
})
```
