# 调试体验、目标资源、C++ 类型与模型评估

承接 [Spec 03](spec-03.md) 的类型系统和工具体验工作。

## 调试体验与 C++ 支持

### 已定事项

- `m.fromDwarf(name)` 接受运行时字符串。解析失败在调用处报告。静态可确定且能解析的名称继续参与精确类型推导。
- `$format()` 默认把 C `char[N]` 展示为字符串，最多读取 `N` 字节，在首个 NUL 处停止，并遵守字符串展示上限。没有 NUL 时按有界字符序列展示。`$toJS()` 是否同步返回字符串待定。
- MCP 已提供 `gdb`，其中 `c` 继续执行并等待停点。补充分离、暂停和立即恢复的工具入口。沿用 `gdb` 命令还是增加 `debug({action})` 待定。
- `fmt` 直接打印已落地。结构化数据继续由 `dbg` 等 API 提供，`fmt.sprintf()` 和字节数组版 `fmt.hexdump()` 返回字符串。

### 待排期建议

1. 调用栈与 `symbolAt` 共享底层符号查找和缓存，为结构化结果提供 `demangledName`，展示优先采用可读名称。调用者帧使用 `lookupPc`，区分符号区间命中和最近符号候选。
2. 从 DWARF 导入枚举成员名及其数值。`$format()` 默认显示已知名称，例如 `UV_SIGNAL`，未知值显示数值。`{enums: "raw"}` 始终显示数值。
3. 为 `$toJS()` 和 `$toJson()` 补空指针与 BigInt 示例。普通空指针在 `$toJS()` 中为 `null`，在 `$toJson()` 摘要中显示为十六进制地址字符串。`$toJS({pointer: "string"})` 只转换地址值，64 位整数仍为 BigInt。序列化报错时提示使用 `$toJson()`。
4. 补齐基本控制动词的 MCP 入口，并在速查中区分继续并等待停点与立即恢复。
5. `layout()` 按 C 声明展示指针成员及偏移，例如 `uv_loop_t *loop; // byteoffset: 8`，避免在成员行展开 pointee。
6. 文档说明 `m.cStr().at(addr)` 读取指针槽位，字符串首地址用 `dbg.memory.readCString(addr, maxLen)` 读取。
7. 明确 `withFormatter()` 返回新的类型描述符。审视声明签名时保留接收者的具体类型和方法链，并补充 `m.self()` 示例。
8. 错误信息给出可执行的下一步。`p`/`ptype` 说明支持当前帧中的裸局部变量和形参，并区分不支持的表达式、变量不存在和值不可读。DWARF 类型找不到时提示 `m.findTypes("*Name*")`。考虑让 `deref: true` 表示默认深度。
9. 在 Quick Start 集中说明 `attach`/`run` 默认 running、`$format()` 默认 `deref: 2`，以及 `maxElements` 控制序列、`maxFields` 控制字段。
10. 保持 `fmt.*` 作为主命名空间，以 `fmt.backtrace` 为主名。现有 `pVar`、`pType` 的去留及 `pBacktrace` 兼容别名待定。工具描述提供一屏速查。
11. 从 DWARF 声明独立取得栈帧变量和形参类型。即使值被优化掉或内存不可读，只要声明类型已知，`ptype` 仍应显示它。
12. 用同一运行时地址和原始回包核对 `addrToLine` 的差异，检查调用者帧 PC、模块地址换算及行表覆盖。按确认的缺口决定是否增加符号级源码回退。
13. 评估 `fmt.symbols({pattern})` 的字符串模式、`fmt.disassemble(addr, count)` 简写和 `fmt.hexdump(addr, len)` 重载。`fmt.memory(addr, len)` 已覆盖按地址读取并直接打印的场景。
14. 增加[运行时数据流追踪](#运行时数据流追踪)，从一次 socket 接收或用户指定的内存范围出发，记录已观测到的读取、复制和后续用途。

#### 运行时数据流追踪

- 首期追踪限定的 live 调试会话。从指定 socket 的一次成功 `read`、`recv` 或 `recvfrom` 返回开始，按实际返回字节数确定用户态缓冲区。也支持手动指定地址和长度。`readv`、`recvmsg` 等分散缓冲区作为后续范围。
- 复用系统调用捕获和断点。在已知的复制函数和输出边界记录源范围、目标范围及重叠字节，例如经过 `memcpy`、`memmove` 转入另一个缓冲区，或作为 `write`、`send` 的参数。用调用返回值区分请求发送的字节与实际发送的字节。硬件观察点可辅助定位所选地址的访问指令，覆盖范围和槽位受硬件限制。
- 按事件给出线程、指令或函数、源与目标地址范围，以及可解析的符号、源码位置和内存映射；有足够 DWARF 信息时补充变量及字段。共享缓冲区由其他线程消费时，记录实际观测到的消费线程。覆盖或释放已被观察到时结束该范围的追踪，避免把地址复用误认为数据仍在传播。
- 限定追踪时长、事件数和活跃地址范围，报告未覆盖的路径及停止原因。相同字节只能作为搜索线索。
- 首期验收用本地 socket fixture，验证一次短读后，接收缓冲区的子范围经 `memcpy` 进入堆对象，并被后续输出消费。结果应能列出源地址、实际长度、目标地址及消费位置，缓冲区复用和另一处相同字节不得产生虚假的传播记录。

##### 进程内 Unicorn 指令级插桩

- 在选定的调试目标进程中加载 Unicorn 动态库和追踪组件。在 socket 读取返回或用户指定的停点，保存所选线程的执行上下文，把 PC、通用寄存器、标志位及该架构所需的其他状态交给 Unicorn，接管该线程的一段用户态执行。首版限定单线程片段。目标映射、写入何时对其他线程可见、退出时如何交回状态，需要在原型中验证。
- 以接收缓冲区的有效字节为来源，利用指令和访存 hook 追踪它们对寄存器、读写地址、写入值和分支条件的影响。分别记录写入目的范围、受影响的分支及其实际走向。覆盖写更新相应来源标签。首期覆盖内联复制和由输入直接影响的条件分支，分支之后的隐式控制依赖留待后续定义。
- 遇到系统调用、信号、无法处理的指令或需要其他线程推进时，结束当前片段并记录原因。在可交接的边界恢复线程上下文，保证已执行的内存副作用只生效一次；无法安全交回时保持目标暂停并报告状态。
- 目标侧用固定容量的简单 ring deque 传出事件。首版单生产者、单消费者，记录单调序号、线程及片段标识、指令地址、事件类型和来源/目的，分支事件补充分支结果。调试器分批读取。队列满时允许丢弃事件，并用丢失计数和序号缺口标明追踪不完整。
- 调试器侧按块压缩归档，优先复用现有 zstd 依赖。归档记录事件格式版本、目标架构、模块映射和构建 ID 等离线符号化所需信息。之后按需解压，重建从输入到目标内存和分支的影响路径，并在缺失事件处保留断点。
- 原型验收使用本地 socket fixture，用短读输入驱动内联复制和条件分支。核对内存目的地址和实际分支走向；验证片段退出后能恢复执行、队列溢出能被识别、归档解压后能复现完整片段的影响路径。

### C++ 标准库

#### DWARF 类型名称匹配

- 优先按真实限定名查找。根据 DWARF 父作用域拼接限定名，命中 typedef 后沿 `DW_AT_type` 获取实际类型。
- 真实限定名未命中时，复用现有 C++ 名称规则生成标准库简写的候选。优先比较 DWARF 模板参数和类型引用，缺少结构化元数据时解析模板名称。识别已知的标准库 ABI 命名空间，仅在默认模板参数一致时允许省略。例如 `std::vector<app::MyType>` 匹配采用 `std::allocator<app::MyType>` 的实例，自定义 allocator 可用完整名称查询。
- 返回目标的原始 DWARF 类型，保留模块、ABI 和实际限定名。指向同一类型记录的 typedef 和类定义可去重，存在多个有效候选时报告歧义。
- 第一批覆盖 `std::string`、`std::string_view` 及对应的宽字符和 UTF 字符别名，以及 `std::vector<T>` 和 `std::array<T, N>`。用固定工具链生成 GCC/libstdc++ 和 Clang/libc++ 的 ELF 与 DWARF 样本，验证标准别名、非类型模板参数、用户类型、自定义 allocator 和 ABI 歧义。标准库头文件作为样本生成依赖。
- 第二批考虑 `map`、`set`、`unordered_map`、`unordered_set`、`deque`、`list` 和 `forward_list`。后续考虑 `pair`、`tuple`、`optional`、`variant` 和智能指针。`std::pmr` 别名保留其 allocator 语义。

#### 值展示

- 基于目标 DWARF 验证字段和偏移，内置适配器直接生成有界预览。第一批覆盖 `string`、`string_view`、普通 `vector<T>` 和 `array<T, N>`。`vector<bool>` 的压缩布局单独处理。未知布局回退普通字段展示。
- 后续优先展示 `map` 和 `unordered_map` 的键值对，再扩展其他容器和智能指针。沿节点读取时遵循元素和读取预算。

### Type System 类模板

```ts
const Pair = m.template((T, U) => m.class({
    first: T,
    second: U,
}, { name: "app::Pair" }));

fmt.pType(Pair);
const Concrete = Pair.of(m.i32(), m.u64());
fmt.pType(Concrete);
```

- `m.class(fields, options?)` 的名称可选，放在字段之后的选项中。名称用于展示。绑定到目标模块的持久化规则以模块构建和原始 DWARF 类型标识为准。
- 未实例化模板保留参数与类定义，支持 `fmt.pType()` 和 `.of()`。实例化后的描述符提供大小、对齐和 `.at(address)`。模板定义展示类型参数，实例布局展示实际字段类型和偏移。
- 复用现有两遍编译。第一遍从内联回调的位置形参提取数量和位置。对可静态解析的 `.of()`，在第二遍的检查副本中注入实例的具体类型。脚本仍按原始代码执行，由 `.of()` 把实际描述符传给回调并校验参数和布局。
- 实参只能在运行时确定时，静态返回类型退回 `Type.Base<unknown>`。能静态解析时，验收覆盖不同参数数量、嵌套字段、数组和指针的精确推导，以及未实例化模板直接调用 `.at()` 的诊断。`m.self()` 在实例内绑定到自身，递归模板和非类型参数可分别验收。

## C 调试优先项

- P0 优先修复跨模块全局变量查找、灵活数组展示、`long double` 类型保真和 DWARF 枚举。查找先尊重当前作用域及局部变量遮蔽，再用符号表缩小全局候选范围，必要时搜索其他模块的 DWARF。同名全局定义应报告歧义。未知长度的灵活数组以内联提示保留其他字段，单次展示可后续支持按字段提供长度。对未支持的 `long double` 保留类型名和布局信息。枚举默认展示已知名称，`enums: "raw"` 保留数值。
- P1 完善有界 `char[N]` 字符串展示、backtrace 和 `symbolAt` 的共享符号解析、`layout()` 的指针声明、字符串首地址读取说明、`wchar_t` 可选字符展示和静态字段偏移的 `Type.fromField()`。以 GCC 和 Clang 样本验证 `_Atomic` 的 DWARF 表示和读取语义。
- P2 放宽 `fromDwarf` 的静态字符串限制并保留可解析名称的精确推导。补齐 MCP 执行控制入口、`fmt` 速查、错误处理指引、默认值说明、`withFormatter()` 类型保留验收及 `fmt.symbols(string)` 和 `fmt.disassemble` 数量简写。
- 类型构造、布局验证和 `Value` 沿用现有 JS 实现。Rust 保留现有 DWARF 解析与导入职责，Rust 类型图和布局引擎迁移不纳入本轮规划。

### Linux 目标进程资源查询

### 目标

在调试会话中，从目标线程、系统调用参数、文件描述符或内存地址定位对应的 Linux 内核资源。优先回答「这个线程在等什么」「这个连接对应哪个 fd」「为什么打开文件失败」和「进程为什么突然变慢或退出」。本节扩展 [spec-03 的进程上下文需求](spec-03.md#默认文档增强)。

由目标所在主机的 `aidbg-server` 通过 Linux 提供的只读接口采集。查询可在目标运行时进行，无需向目标注入代码或让目标执行系统调用。

### 第一阶段：文件描述符和等待关系

- 提供结构化查询，候选脚本入口为 `dbg.resources.fds()` 和 `dbg.resources.fd(fd)`。通过 `/proc/<pid>/fd` 和 `fdinfo` 识别普通文件、设备、管道、FIFO、socket 和匿名 fd。返回可获取的路径、inode、挂载 ID、读写及状态标志、当前位置，以及文件已删除但仍打开的状态。管道展示端点类型，权限允许时可补充其他持有者。
- 解码 epoll 监听项及事件掩码、eventfd 计数、timerfd 剩余时间和周期、signalfd 信号掩码、inotify 和 fanotify 监听项。关联 epoll 监听项和当前 fd 时核对可用的对象标识，fd 已关闭或复用时保留监听记录并标明关联状态。
- 在目标的网络命名空间视图中，用 socket inode 关联 TCP、UDP 和 Unix socket。展示适用的本地端点、对端、状态和收发队列。
- 结合线程状态、当前系统调用及内核等待点，把系统调用的 fd 参数关联到资源。例如从 `epoll_wait(3, …)` 查到 epoll 实例、监听项及其 socket 端点。在脚本中可显式把 `conn->fd` 等表达式结果用于资源查询。系统调用参数按已知语义解码，普通整数由调用方明确指定为 fd。

数据来源见 [Linux procfs 文档](https://docs.kernel.org/filesystems/proc.html)。

### 第二阶段：地址空间和进程上下文

- 扩展现有映射查询，按地址展示映射范围、权限、文件偏移和后备对象。按需提供 RSS、脏页及可识别的共享内存信息。建立映射时使用的 fd 关闭后，仍可从地址定位当前映射。
- 展示目标所属命名空间、挂载和 cgroup。区分目标持有的对象和目标所在命名空间可见的对象。System V 共享内存、消息队列和信号量等没有明确持有关系时，按命名空间展示。
- 对 `futex(addr, …)` 等等待，把地址关联到映射，并在 DWARF 和运行时信息足够时关联到用户态锁变量。持有者仅在能依据具体锁实现可靠解码时展示。
- 关联文件锁、等待者、设备号、inode 和字节范围。展示线程及进程待处理的信号、线程掩码和信号处置方式，以及 UID、capabilities、seccomp 模式和资源软硬限制。排查 `EMFILE` 时可并列展示当前 fd 数量与 fd 上限。

数据来源见 [Linux procfs 文档](https://docs.kernel.org/filesystems/proc.html)及 [cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)。

### 第三阶段：资源压力和事件

- 内核提供任务延迟统计时，比较两次采样之间的 CPU 等待、同步块 I/O、换入和内存回收等累计时间变化。结合调用栈和等待点理解延迟来源。见 [Linux delay accounting](https://docs.kernel.org/accounting/delay-accounting.html)。
- 按需展示目标 cgroup 的 CPU 节流、内存限制与 OOM 事件、I/O 用量，以及 CPU、内存和 I/O 压力。cgroup 计数提供组级上下文，单个进程的退出原因需要结合目标事件判断。见 [cgroup v2 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)和 [Linux PSI 文档](https://docs.kernel.org/accounting/psi.html)。

### 采集语义

结构化查询供脚本使用，摘要按需纳入现有进程上下文。运行中读取多个接口得到的是各自采样时的观测。目标退出、fd 复用、权限不足或内核未提供某项数据时，保留已取得的结果并标明缺失原因。

### WSL 产物生成与自动验收

- 提供可在 Ubuntu WSL 使用的准备脚本，负责构建、执行正常对照、验证故障症状并保存产物。libuv 对照须在时限内退出，故障组须先完成初始化并在时限到达时仍未退出。脚本失败时输出对应构建或验收日志。
- 仅动态符号档使用无 `-g` 构建并剥离静态符号。脚本用 `readelf` 确认目标没有 DWARF、`.symtab` 或外部调试链接，仍保留 `.dynsym` 和 unwind 信息。评测环境禁用 debuginfod，避免独立调试包补回题目涉及的模块符号。
- 对已确认的本地故障命令，GDB 批处理在 `SIGSEGV` 停止后自动执行 `generate-core-file`。脚本检查实际停止信号和非空 ELF core，同时记录匹配的可执行文件、共享库及构建 ID。已有 core 可以直接入题。OpenCV 可用于正式评分的前提是配齐可核验的现场与匹配构建。
- 参测模型只收到题面和该档需要的程序、core、共享库及符号文件。故障生成源码、对照日志、GDB 采集日志及标准证据留在出题方。脚本仅验收产物与症状，定位与解释由参测模型完成。

## 实际模型能力评估

### 测试设置

- 对每个实际模型使用供应方支持的思考强度运行相同用例，至少对照低、高两档。各档使用相同提示、工具描述、目标初始状态和任务预算，每个用例独立重复运行。记录模型及版本、思考强度、用例、运行编号、aidbg 客户端和服务端版本，以及本次测试的环境和预算。
- 用例分为工具使用题和故障定位题。工具使用题明确要做的操作，例如选择帧、读变量或等停点，便于量化模型使用工具的开销。故障定位题可复用 [调试用例及预期结果](../tests/debug-cases/README.md)，分别判断定位结论和工具使用过程。

### 记录与统计

| 指标 | 统计口径 |
| --- | --- |
| 思考消耗 tokens | 优先取模型 API 报告的 reasoning tokens，按请求记录并按任务汇总。记录调用前推理的对应请求和工具等待时间。供应方未暴露的字段记为不可用。 |
| 工具使用思考开销 | 单独汇总工具使用题的 reasoning tokens，以及从任务输入或上次工具返回到下一次工具调用的耗时，工具执行耗时单独记录。故障定位题中只有能从任务划分或记录明确归因的开销才记入工具使用，混合回合单列。使用 token 数和耗时评估，无需采集思维链文本。 |
| 错误频率 | 记录每次运行的错误数、出错工具调用数，以及出错工具调用数除以工具调用总数。同时报告任务成功率和完成情况，以便识别跳过必要调用或提前结束。 |
| 重复错误频率 | 在同一次运行内，如果工具返回或文档已提供可用反馈，随后仍因同一根因出错，计为重复错误。例如改写参数后仍违反同一调用约束。报告重复错误数、它占模型工具错误总数的比例，以及发生重复错误的运行数。 |
| 常见错误 | 按根因归类并记录次数、受影响用例、代表性调用和反馈。例如工具选择错误、参数或类型错误、未等待异步结果、帧或线程状态误判、误读回包。版本不匹配、工具故障和预期的探测失败单独记录。 |

### 预期表现

- 低思考强度应能稳定完成常见调试操作，保持较低的工具错误率和重复错误率。
- 高思考强度应熟练完成相同的工具操作，避免在接口选择、参数构造和已解释错误上消耗过多 tokens 或时间。故障根因定位所需的推理可以记录总量，工具使用效率的判定仅纳入可归因的开销。
- 按模型、思考强度和用例类别报告样本数、错误计数、比率、常见错误，以及思考 tokens 和工具调用前耗时的中位数与长尾。先以实际模型结果建立基线，再确定量化阈值。
