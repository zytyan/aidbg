# aidbg 断点脚本与线程限定设计

每次活进程脚本使用独立的 QuickJS runtime，同一脚本注册的回调可共享闭包。命名导出在目标会话内共享模块状态。MCP 保留独立的进程控制和断点操作，并通过服务端的 `$` 命名空间引用跨调用复用的导出。断点和观察点可以绑定到一个具体的 Linux 线程。

硬件配置来自会话槽表，软件断点按地址查找。活进程和离线 core 都通过 `script_run` 执行脚本。 [断点安装与分发](../src/breakpoint.rs) · [规则加载](../src/breakpoint/rules.rs) · [脚本执行](../src/script.rs)

## 顶层脚本和 MCP 入口

`script_run({run_id, source})` 在目标的 tracer 会话中执行脚本，返回本次安装的断点 ID 和默认导出函数的返回值。`script_api({mode: "live"})` 提供活进程声明。离线 core 使用 `script_run({target_id, source})` 和原有声明，两个目标参数互斥。

调用方可以先用现有 MCP 工具取得地址和目标线程的 TID，再提交下面的脚本。

```ts
let hits = 0;

dbg.hardwareBreakpoint(
    0x401020n,
    hit => {
        hit.emit("hits", ++hits);
        if (hits === 3) hit.disable();
    },
    { tid: 1234, timeoutMs: 50 },
);
```

`dbg.hardwareBreakpoint(address, callback?, options?)` 在调用处安装断点，返回带 ID 的 handle，安装失败时抛出错误。回调缺省时使用默认快照行为。`options.tid` 缺省时，断点适用于目标的全部线程。软件执行断点阶段可增加同样的同步方法 `dbg.softwareBreakpoint`。

MCP 的 `breakpoint_set` 增加可选 `tid`，与现有 `pid` 或 `run_id` 组合。返回结果带上配置的 `tid`，命中事件的 `tid` 表示实际命中线程。`all_threads` 继续选择快照范围，因此线程限定断点也可以请求全进程快照。CLI 可用 `breakpoint set --tid` 表达同一选择。脚本、MCP 和 CLI 共用安装后端。

入口暂停的目标在安装后保持暂停，直到调用 `dbg.continue()` 或 `run_continue`。用 `await dbg.events()` 可在同一次脚本调用中等待目标退出，并读取本次安装的断点事件。脚本失败时回滚本次断点安装，结果中的 `breakpoint_ids` 为空，本次断点的事件也不会进入日志。

## 会话 runtime 与闭包

每个活进程 tracer 会话在自己的线程上拥有一个共享 runtime。tracer 从现有命令队列接收脚本请求，使用现有控制流程取得安装所需的停点，先处理已经到达的命中，再同步执行脚本顶层。顶层安装结束后，tracer 按目标原有运行状态恢复。顶层 JavaScript 执行期间禁止嵌套分发 `onHit`。

`dbg.hardwareBreakpoint()` 直接调用同一 tracer 线程内的安装逻辑。`onHit` 则在后续停点到来时由现有的 tracer 循环调用。两次进入 QuickJS 都同步完成，因此这一阶段只需现有的停点循环。目标命中的等待发生在独立的调用之间。

- **内联回调**保留脚本中的函数对象。两个断点传同一个函数就共享闭包，分别调用函数工厂就得到两份独立状态。每次 `script_run` 有自己的模块作用域，已安装断点继续持有引用的函数及闭包。断点移除、自动撤销或目标会话结束时释放相应引用。
- **已登记模块**按模块和版本在每个目标会话内初始化一次。相同导出绑定到多个断点时共享该模块的状态。不同目标会话分别初始化。断点的启停、命中序号、暂停预算和事件按断点记录。
- **现有入口** `rule_source`、`rule_id` 和 `defineRule` 保持按断点初始化及计数的契约。旧式装载可以先沿用现有独立 runtime，迁移时继续为每个断点创建隔离的模块环境。
- **上下文寿命** `hit.inspect()`、`hit.memory()`、`hit.emit()`、`hit.snapshot()` 和 `hit.disable()` 只在本次同步回调中有效。寄存器值及 `DataView` 持有的内存副本可以留在闭包中。通过闭包拿到的 `dbg.hardwareBreakpoint()` 在回调期间拒绝重入安装。

`timeoutMs` 是每次命中的暂停预算，由回调、读取和快照共用。多个线程在同一批次命中时，tracer 按现有停点顺序依次调用回调。回调返回 `false` 时恢复目标并省略该次成功命中的事件和快照。

顶层脚本和回调都要求同步完成。普通回调异常或超时生成诊断事件，并撤销当前断点。若有违规的待处理 JavaScript 任务，或引擎无法继续使用，释放受影响的 runtime 和它管理的回调断点，再完成目标恢复。共享 runtime 的执行路径只接受同步返回。

## 命中输出的值和字节

`hit.emit(label, value, options?)` 每次追加一条有名称、有类型的记录。记录在 tracer 中保存为对应的整数、浮点数、地址或字节序列。输出以字段为单位，脚本可以分别记录 C 结构体的成员，也可以直接记录一段内存。

| 输入 | 输出表示 |
| --- | --- |
| `bigint` 或安全整数 `number` | 同时显示十进制和十六进制，如 `42 0x2a`、`-42 -0x2a`。使用 `bigint` 保留大整数精度。 |
| 浮点 `number` | 显示十进制数值和标明 `f64` 的 IEEE 754 十六进制位模式。 |
| `bigint` 配合 `{ kind: "pointer" }` | 作为地址只显示十六进制，如 `0x401020`。显式标记用于区分普通整数和指针。 |
| `DataView` 或 `Uint8Array` | 按视图的 `byteOffset` 和 `byteLength` 取字节，保留内存顺序。对外输出两位小写十六进制文本，每字节保留前导零，字节之间用一个空格分隔，如 `0a 0c 33 36`。字节项省略 `0x` 前缀。 |
| 字符串、布尔值或 `null` | 记录单独的文本、布尔值或空值。 |

```ts
const read = hit.memory(hit.address, 4);
if (read.complete) {
    hit.emit("word", read.view.getUint32(0, true));
    hit.emit("bytes", read.view);
}
hit.emit("address", hit.address, { kind: "pointer" });
```

字节记录固定在调用 `emit()` 时的内容。视图之后的写入只修改脚本自己的副本。读取不完整时，脚本仍可输出视图中的已读字节，并单独记录 `complete`。

`emit()` 的内容通过 `callback.output` 作为结构化字段返回，整数按 JSON 整数编码。MCP 同时返回文本字段行，指针使用十六进制。

## 跨 MCP 调用的导出

`$` 由服务端管理，表示该服务端实例已登记的 QuickJS 命名导出。MCP 会话重连后仍可查找这些导出，服务端重启会清空这份内存注册表。脚本内部调用本模块函数时直接用函数名，`$` 保留给 MCP 参数中的引用格式。

用现有 `rule_define` 增加显式的 `mode: "exports"` 登记命名回调：

```ts
export function someHit(hit: BreakpointHit) {
    const pc = hit.registers.pc ?? hit.registers.rip;
    if (pc !== undefined) hit.emit("pc", pc, { kind: "pointer" });
}
```

后续 MCP 调用可独立指定导出和线程：

```json
{
  "run_id": "run-example",
  "kind": "hardware",
  "address": "0x401020",
  "tid": 1234,
  "handler": "$.someHit",
  "timeout_ms": 50
}
```

- `handler`、`rule_id` 和 `rule_source` 互斥。第一版发布显式命名的同步函数，安装时按「模块 ID、版本、导出名」解析和验证。
- `$` 是只读注册表。登记模块遇到同名导出时整次失败。显式 `rule_update` 可以发布同一模块的新版本，保留已有名称的所有者。更新在隔离的模块环境中初始化候选版本，校验正在使用的每个导出，并在目标会话的命中批次边界统一切换。候选模块初始化期间不执行目标控制操作。验证失败时旧版本继续服务。
- 再次引用同一个名称复用已登记的代码。运行态的模块变量和闭包由实际目标会话持有。删除仍被断点引用的模块会失败。

## 线程限定执行断点

线程选择绑定到目标线程组内的一个已跟踪线程。安装阶段验证 `tid` 的成员身份和线程寿命，再提交配置。内部使用 TID 与 tracer 的线程身份记录匹配，并在确认线程退出后撤销该线程的断点。TID 被系统复用时，新线程按自己的身份注册。新建线程会继承适用于全进程的配置，线程专属配置只属于原选定线程。

| 断点类型 | 安装与恢复 | 非选定线程经过同址时 |
| --- | --- | --- |
| 硬件执行断点 | 仅向选定线程写入硬件槽。每个线程用自己的槽表，将内核停点解析到逻辑断点 ID。x86_64 用该线程的触发槽位，AArch64 在该线程已安装的规则里匹配报告地址。 | 该断点本身不会使其他线程停住。安装、恢复或快照仍可能按 tracer 的需要短暂冻结其他线程。 |
| 软件执行断点 | 指令补丁位于进程共享的代码映射里。处理 trap 后按线程选择逻辑回调。单步执行原指令和重装补丁仍经过现有的同进程冻结流程。 | 可能进入 debugger 的 trap 恢复路径。执行原指令并恢复线程，跳过逻辑命中、回调、计数、快照和事件。 |

第一阶段允许为不同 TID 在同一个地址各装一个硬件执行断点。对同一线程覆盖范围有重叠的重复安装返回冲突，包括全线程断点与同址的线程限定断点。实际槽位按线程分配，并与已有观察点共同计算平台容量。安装或移除中途失败时恢复先前配置。软件断点阶段沿用每个地址一个补丁的表示，先支持单个逻辑线程限定断点。

线程退出、目标退出、地址空间更换和分离时清理相应规则及其回调引用。保留已经产生的事件。线程消失后，对应的线程限定断点自动撤销。

## 实施顺序和验收

1. **线程限定硬件执行断点。** 从 MCP、CLI 和已有 tracer 入口验证两个线程执行同址时仅指定 TID 命中。覆盖两个 TID 同址各有一个断点、槽位耗尽回退、新线程、线程退出和 TID 复用。在 x86_64 和 Raspberry Pi AArch64 上验证命中归属及恢复。
2. **共享 runtime 与顶层安装。** 验证顶层脚本直接安装内联函数并返回断点 ID，两个断点复用同一个闭包时共享计数，用函数工厂时分别计数。用 D09 验证脚本安装、MCP 继续及命中后的 DWARF 读取。覆盖重复安装、运行中的安全停点、返回 `false`、回调超时及目标退出。
3. **跨调用命名导出。** 从一次 MCP 调用登记模块，在另一次调用通过 `$.someHit` 安装线程限定断点。验证同名登记失败，热更新保留断点 ID，删除正在引用的导出失败，以及不同目标会话独立初始化。
4. **命中输出。** 验证大整数的十进制和十六进制保留精度，指针只显示十六进制，非零偏移的视图只复制视图范围内的字节，字节输出严格匹配 `0a 0c 33 36` 这样的两位小写十六进制序列，修改源视图后已记录内容保持原值。
5. **线程限定软件断点。** 验证其他线程经过同址时仍正确执行原指令，同时只记录指定线程的命中。覆盖连续命中、多个线程同时停住、拆除补丁和 fork 清理。
